## 证据与根因

1. **1w4g 的 refresh token 已被服务端吊销**：直接调用
   `POST account.minimax.cn/oauth2/token`（grant_type=refresh_token）返回
   `HTTP 400 invalid_grant — "this refresh token can no longer be used, start a new authorization"`。
   工具的 401 抢救路径（强制刷新→落盘→重试）已正确执行，但刷新本身被上游拒绝，无凭据可落。
2. 吊销原因：修复上线前，该账号曾在客户端登录后又切走/重新登录，旧会话连同 RT
   一起被作废（MiniMax 单会话策略，与 Cockpit Tools 文档描述的行为一致）。
3. **修复有效性已被 7bD8 反证**：客户端完全未运行（其 auth.json 文件 token 已过期
   2 小时以上且 401），7bD8 依靠池内 RT 自动刷新连续存活，两轮观测到
   「刷新 → RT 轮换 → 落盘 → 新 token 探活 200」完整循环，节奏约每小时一次。

## 修复引入的回归（第 12 轮发现，已修复）

- **2026-10-27 06:39–06:55 流水刷屏**：「失败可重复落盘」的新规则与调度器行为叠加
  出问题——调度器在时间窗内对失败账号**每 ~30 秒重试一次**，旧代码调度器失败
  不落流水，新规则下死账号 16 分钟被刷了 32 条相同失败。
- 修复：`record_result` 对 failed 增加 **10 分钟节流**（`logging::has_recent_failure`），
  同账号 10 分钟内只落一条——调度器重试不再刷屏，手动重试的失败证据仍保留。
- 已按新规则清理当日刷屏存量（32 条 → 3 条，原始备份 `logs/*.bak-flood-20261027`）。
- 教训：改「什么结果落流水」时必须同时考虑**调度器的重试节奏**，不只是手动触发。
